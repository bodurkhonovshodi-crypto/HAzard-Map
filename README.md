# Pamir Hazard Watch

A web app about natural hazards in Gorno-Badakhshan: a live hazard map with weather warnings, all the data to download,
the story of past disasters, and a "what if" storm simulation.

## What's new in this version

**New design: "field atlas".** Warm map-paper background, ink text, thin rules, Newsreader serif headings,
IBM Plex Sans for the interface and IBM Plex Mono for small labels. The only strong colours are the alert levels
(green = Normal, ochre = Watch, red = Warning) and one slate-teal accent for links and selected buttons.
All colours are at the top of `css/style.css`. The page is now light-only, so maps and printouts look the same everywhere.

**Fixes**

- **Forecast window** (`js/home.js`): the app now looks at today, tomorrow and the day after. The 3-day snow total is
  checked for every 3-day window ending on those days, so a storm forecast for tomorrow also counts in the 3-day total
  (before, only the past 2 days + today were added up).
- **Desktop alerts** (`js/home.js`): a valley that drops below Warning can alert again the next time it reaches Warning
  (before, each valley could only alert once per page visit).
- **Saved climate data** (`js/simulate.js`): the 30-year statistics saved in the browser are now tied to each valley's
  position and altitude in `data/sections.js`. Change a valley there and the Simulation page downloads fresh statistics.
- **Rockfall above Khorog** (`data/events.js`): marked as `ongoing` (it is the 2020 AKAH survey, not a one-day event);
  its map pin shows • instead of a year.
- The status line now says honestly that only the temperature is corrected for altitude; rain and snow come from the weather-model grid.

**Privacy:** the lists in `source/damaged_houses/` (residents' names) are **not in this zip**. Keep your own copy
on your computer if you need to re-run `tools/damage_lists_to_js.py`, and never upload it anywhere public.

## The app versions (Android app + installable web app)

The web app now lives in **`www/`**. The same files run in three ways:

| How | What you do |
|---|---|
| **Website** | Open `www/index.html` with Live Server (see below), or host the `www/` folder anywhere. |
| **Installable web app (PWA)** | Host `www/` on HTTPS (the included GitHub Pages workflow does this). On a phone, open it and choose **Add to Home screen** / **Install app**. The data, photos, pages and the map tiles you have looked at keep working offline. |
| **Android app** | A real Android app made with [Capacitor](https://capacitorjs.com). Alerts become phone notifications, and download buttons open the Android "save / send" sheet (Files, Drive, Telegram …). |

### Get the Android APK

**Easiest — let GitHub build it.** Every push runs `.github/workflows/android.yml`. Open the repository on GitHub →
**Actions** → **Android APK** → the latest run → download **pamir-hazard-watch-debug-apk** under *Artifacts*.
Unzip it, copy `app-debug.apk` to the phone and open it (allow "install unknown apps" once).

**On your own computer** (needs Node 22+ and [Android Studio](https://developer.android.com/studio)):

```
npm install
npm run android:sync      # copies www/ into the Android project
npm run android:open      # opens Android Studio → Run ▶ on a phone or emulator
```

or build the APK from the command line with `npm run android:apk` (file: `android/app/build/outputs/apk/debug/app-debug.apk`).

**After you change anything in `www/`**, run `npm run build` (updates Leaflet copy and the offline file list in `www/sw.js`)
and `npx cap sync android` before building the app again.

**For the Google Play Store** you need a signed release build (`.aab`): in Android Studio use *Build → Generate Signed Bundle*,
and keep the signing key safe — you need the same key for every update. App id: `org.pamirhazardwatch.app` (in `capacitor.config.json`; change it before the first Play Store upload if you want a different one).

**iPhone:** the PWA works on iPhone today (Safari → Share → *Add to Home Screen*). A native iOS app needs a Mac with Xcode:
`npm install @capacitor/ios && npx cap add ios && npx cap open ios`.

## The four pages

## Open it in Visual Studio Code

1. Unzip the folder and open it in VS Code (**File → Open Folder…**).
2. Install the **Live Server** extension (Extensions panel, search "Live Server" by Ritwick Dey).
3. Right-click `www/index.html` → **Open with Live Server**. The app opens in your browser at `http://127.0.0.1:5500`.
4. Every time you save a file, the browser reloads by itself.

You need internet for the map tiles, the Leaflet library, the forecast and the 30-year climate data.
Live Server is the best way to open it; desktop alerts and some browsers' file loading need it.

## How the Simulation works

1. When the page opens it downloads daily rain and snowfall for 1991–2020 (ERA5 reanalysis, through Open-Meteo)
   for each valley, at the valley's forecast altitude. It is saved in the browser, so it loads only once.
2. For every year it takes the biggest day of rain, the biggest day of snow, and the biggest 3 days of snow.
3. It fits a **Gumbel distribution** to those 30 yearly maxima. That gives the **return level**: how big a storm
   is that comes on average once in T years. Chance in any one year = 1/T; chance in N years = 1 − (1 − 1/T)^N.
4. That storm goes through the same rules as the Map page (`js/rules.js`). Valleys are coloured on the map;
   avalanche and rockfall sites light up when the storm can set them off; the list ranks the most dangerous places
   by alert level, households at risk, avalanche volume and zone intensity.

ERA5 is a 25–30 km grid and smooths mountain storms, so real local extremes are bigger. 30 years is short for
estimating a 100-year storm. It is a teaching and planning tool, not an official hazard assessment.

## Adding more data

### From Excel (same layout as `Avalanch_Rushan_Vanj_Darvoz.xlsx`)

```
pip install openpyxl
python tools/excel_to_js.py "Avalanch_Shugnan.xlsx" www/data/avalanche_db_shugnan.js --id db-shugnan --title "Avalanche database: Shugnan"
```

### From a shapefile (points, WGS 84)

```
python tools/shp_to_js.py "C:/GIS/mudflows_shugnan" www/data/mudflows_shugnan.js --id mud-shugnan --title "Mudflow sites, Shugnan" --hazard mudflow
```

Write the path **without** `.shp`. If the layer is in UTM, first save it as EPSG:4326 in QGIS.

### Rockfall table (same layout as AKAH table 3.2)

The table has no coordinates, so positions are kept in `source/khorog_rockfall_positions.csv` (one line per zone: RF-01, RF-02 …).
I took them from the numbered circles on the AKAH map, so they are **approximate** (within about 100–200 m).
If you know better positions, change the numbers in the CSV and run:

```
python tools/rockfall_table_to_js.py source/Khorog_rockfall_table_3.2.xlsx source/khorog_rockfall_positions.csv www/data/rockfall_khorog_2020.js
```

### A scanned or exported map (JPG/PNG) with a lat/lon grid

Read the pixel position of two longitude ticks and two latitude ticks (Paint or GIMP show x/y under the mouse),
and the corners of the map frame. Then see the example at the top of `tools/image_bounds.py`.
Maps with a UTM grid are not straight in lat/lon; georeference those in QGIS (Georeferencer) and export as GeoTIFF instead.

### A DEM → slope map

```
pip install numpy pillow
python tools/dem_to_slope.py "C:/GIS/my_dem.asc" www/data/overlays/slope_my_area.png --utm-zone 42 --id slope-my-area --title "Slope classes, my area" --js www/data/overlay_slope_my_area.js
```

Works with an ESRI ASCII grid (`.asc`) or an ArcInfo grid **folder** (with `hdr.adf`, `dblbnd.adf`, `w001001.adf`, `w001001x.adf`).
It colors 30–45° slopes (where avalanches start) and slopes over 45° (where rockfall starts).

The four DEMs you sent (all UTM 42N, about 12.5–13.5 m cells) are already in the app as slope layers:

| Layer | Area | Elevation |
|---|---|---|
| DEM A | 37.54–37.66°N, 73.08–73.12°E | 3774–4718 m |
| DEM B | 37.48–37.61°N, 72.73–72.79°E | 3866–5344 m |
| DEM C | Yashilkul west end, 37.67–37.80°N, 72.81–72.87°E | 3689–5142 m |
| DEM D | 37.37–37.47°N, 73.00–73.13°E | 3801–5104 m |

Only DEM C came with an undamaged `dblbnd.adf`. For A, B and D the script used a corner rule found in these grids
(top-left corner = 1024 cells right of and 3072 cells above the point stored in `hdr.adf`). The rule matched DEM C exactly
and the damaged parts of the other files, and Yashilkul lake shows up in the right place, but please check A, B and D in QGIS once.

### Damaged houses

```
python tools/damage_lists_to_js.py source/damaged_houses/*.xlsx --positions source/village_positions.csv --out www/data/damaged_houses.js
```

The script counts houses and people per village. It never copies residents' names into the app.
Villages need a position in `source/village_positions.csv`; 11 of 30 have one now (from the HVRA reports).
Add a line `district_ru,village_ru,lat,lon,source` for each other village and run the script again.

**Privacy:** the Excel lists in `source/damaged_houses/` contain residents' names, so they are not included in this zip.
Keep them only on your own computer. The app itself (`index.html`, `css`, `js`, `data`) has no names.

### Boundaries, roads, population, glaciers (any GeoJSON)

```
python tools/geojson_to_js.py gbao_districts.geojson www/data/layer_gbao_districts.js --title "GBAO districts" --color "#5b4a8a"
```

### A past disaster

Open `www/data/events.js`, copy one block, change the facts, and put the photos in `www/images/events/`.
Write where every number comes from in `sources`.

### New area?

Sites are put into the nearest section from `data/sections.js` (up to 35 km away).
For a new valley (for example Bartang or Ishkashim), add one line there with a name and a point in the middle of the valley.
Sites with no section nearby are still listed but get no weather check.

## How the warning works

1. For each section, the app asks Open-Meteo for snowfall, rain and maximum temperature for the last 2 days and the next 3 days,
   at the altitude set in `forecastAlt_m` (where avalanches start, not the valley floor).
2. `js/rules.js` turns that into Normal / Watch / Warning:
   - lots of new snow in one day, or over 3 days
   - a warm day after fresh snow (wet-snow avalanches)
   - rain on fresh snow
   - heavy rain (mudflow and flood risk)
   - for areas with rockfall zones: heavy rain, or snow melting on the slopes (water loosens rock blocks).
     Earthquakes also trigger rockfall, but they cannot be forecast.
   - June–August: a hot day at forecast altitude (glacier and snow melt), and a hot day with rain → mudflow risk.
     The rain thresholds follow the OSCE report (2018): 15–20 mm a day starts mudflows (Perov 2012).
     Most of the largest GBAO mudflows on atlas map 155 came from glacier melt or glacier-lake outbursts in summer.
3. Sections with Watch or Warning get an alert message. With **Turn on desktop alerts**, the browser also shows a notification.
   The forecast refreshes every 3 hours while the page is open.

The thresholds are drafts. Check them against past avalanche dates and talk to specialists before anyone relies on them.

## Data problems found

- **Rows 1–36 of the 2017 Excel table (Rushan: Vomar to Shipad)** all have almost the same placeholder GPS point
  (`37.565268, 71.35075…`), so they are not on the map. The table shows them as "No GPS". Add real coordinates in Excel and run the converter again.
- **Row 37**: latitude 37.09 looks wrong (maybe 38.09). **Row 80**: Poi Mazor is about 45 km from row 79, same village.
  Both are listed as "Check GPS". After you fix them, remove them from `SUSPECT_ROWS` at the top of `tools/excel_to_js.py`.
- **Row 56**: longitude `7040359` was read as `70.40359`.
- **Rockfall table**: positions come from the map labels, not from GPS. RF-04, RF-06, RF-07, RF-08, RF-18, RF-19 and RF-20
  have several parts (участки) under one number; the app shows them together in one popup.
- **Shugnan database 2017**: 97 rows are marked "Лавина_база" with a count but no coordinates or data of their own, so they are not on the map.
  The CSV copy of this table lost all Russian letters (saved without UTF-8); the app uses the Excel file.
- **KML zones**: only 25 of 145 polygons have attributes (return period, intensity). "BAZA" in a name is kept as it is.
- **HVRA Ishkashim report**: the village coordinates are written in UTM with typos. Rin and Kozideh were fixed by hand (approximate);
  Yakhshvol does not fit and is left without a position.
- **Atlas mudflows**: positions read from a photo, about ±10 km, shown as dashed circles.
- **Shapefile**: some Russian notes were saved as `????`. Exporting the layer again from QGIS with **UTF-8** encoding should keep them.
